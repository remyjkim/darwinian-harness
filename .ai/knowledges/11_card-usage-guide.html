drwn Cards and Workers

Author Cards → compose one Blueprint → add roots → select one Worker → write.

Terms

TermMeaning
CardAn independently authored and published capability bundle: skills, MCP definitions, hooks, and optional Mind content.
BlueprintA Card with an ordered list of plain Card members. It defines one composed Worker.
Worker rootAn installed plain Card or Blueprint. Installed roots are alternatives.
Selected WorkerThe single root named by activeWorker, or no root when it is null.
ClosureThe selected root followed by its ordered Blueprint members.

Author And Publish Cards

drwn card new @team/notion --into ~/dev/darwinian-cards/cards --no-git
NOTION_SOURCE=~/dev/darwinian-cards/cards/notion
drwn card source add-skill "$NOTION_SOURCE" notion-knowledge
drwn card source add-mcp "$NOTION_SOURCE" notion
drwn card source doctor "$NOTION_SOURCE" --json
drwn card publish --from "$NOTION_SOURCE"

Editable sources are ordinary repositories selected by path or a unique configured catalog match. Published versions are immutable Store artifacts. Credentials never belong in a Card source or manifest.

Compose One Blueprint

drwn worker new @team/operator --into ~/dev/darwinian-cards/cards --no-git
OPERATOR_SOURCE=~/dev/darwinian-cards/cards/operator
drwn worker compose "$OPERATOR_SOURCE" --add @team/notion@^1.0.0
drwn worker compose "$OPERATOR_SOURCE" --add @team/fal@^1.0.0
drwn worker publish --from "$OPERATOR_SOURCE"

Member order is capability precedence and provenance order. Members must be plain Cards in this contract.

Initialize A Project

cd /path/to/project
drwn init --non-interactive
drwn apply @team/operator@^1.0.0
drwn use @team/operator --no-write
drwn write --dry-run
drwn write

The committed config is self-identifying:

{
  "schema": "drwn.project-config",
  "schemaVersion": 1,
  "workers": ["@team/operator@^1.0.0"],
  "activeWorker": "@team/operator"
}

workers lists only roots. Blueprint members are resolved into card.lock.

Manage Roots And Selection

drwn add @team/alternate@^1.0.0
drwn apply @team/operator@1.0.0 @team/alternate@1.0.0 --active @team/operator
drwn pin @team/operator@1.0.0
drwn update @team/operator
drwn remove @team/alternate
drwn use @team/operator
drwn use --none

Adding alternatives does not combine them. Composition changes happen by publishing a different Blueprint. Root mutations update config and lock atomically; selection changes do not alter the lock.

PathRole

.agents/drwn/generated/active-worker.jsonDisposable selected root and closure record.

A Blueprint root receives one aggregate generated directory. Its member Cards do not receive sibling Worker directories unless they were separately installed as roots.

Project Capabilities

Project declarations come from the selected closure and explicit project overlays. The selected machine Worker is a separate machine-write authority and is never inherited. User-home skills and MCP entries may still be visible to downstream tools; status and doctor report those as ambient, never as project declarations.

drwn status --json
drwn status --why skill:notion-knowledge
drwn doctor --json

Notion And External Tools

Cards can ship a Notion MCP definition or an ntn integration skill, but OAuth and API keys remain operator state. Complete Notion OAuth in the downstream client and keep API keys in environment or secret storage. External stdio tools such as Momentic must be installed and authenticated separately.

An OAuth-required or missing-executable startup error is a runtime readiness issue. It does not mean the project root graph is invalid.

Clone And Install

drwn install --frozen
drwn install --no-write
drwn write --dry-run
drwn install

Install hydrates the exact lock and writes by default. It does not change root requirements or selection.

Capture And Deploy

drwn card new @team/captured --from-project . --into ~/dev/darwinian-cards/cards
drwn worker deploy @team/operator@1.0.0 --name team-operator

Project capture includes the selected closure and explicit overlays, excluding inactive roots, machine/ambient capabilities, generated output, platform connectors, and secrets. --from-defaults separately flattens only the active machine closure into a plain Card. Project-aware deploy sends one root plus pinned closure through the unchanged remote contract. Member and inactive-root deploy attempts fail locally.

Machine Worker Blueprint

Machine intent uses strict drwn.machine V2. It selects one canonical Worker name and embeds the immutable closure lock. V1 profile and bare skill/MCP selections are rejected, not migrated or dual-read.

{
  "schema": "drwn.machine",
  "schemaVersion": 2,
  "policy": {},
  "capabilities": {
    "activeWorker": null,
    "workerLock": null
  }
}
drwn apply --root <published-blueprint-ref>
drwn use --root <installed-name-or-ref> --no-write
drwn card trust <card> --hooks --scope machine
drwn card trust <card> --instructions --scope machine
drwn write --root --dry-run
drwn write --root

activeWorker stores the canonical Card name; workerLock.workerRoots[].requested stores the versioned Store/pinned Git ref or an explicit integrity-locked file ref. File-origin bytes are re-hashed before projection. Runtime resolution never searches mutable authoring checkouts. Guided init may offer the recommended @curation-labs/machine-defaults Blueprint; non-interactive or declined setup remains empty.

The active closure can project skills, MCP definitions, one generated aggregate Worker, consented hooks, and consented instructions. Machine instruction adapters are ~/.claude/CLAUDE.md and ~/.codex/AGENTS.md; drwn never creates ~/AGENTS.md.

Standalone skill packages and MCP records remain inventory. The retired drwn machine skill|mcp enable|disable commands fail with Blueprint guidance. Inventory lifecycle and portable transfer commands remain available.

Safety

drwn write is a pure projection and supports --dry-run. It never changes project root requirements, selection, or lock state.

There is no public whole-Store archive command. Use controlled reset for unsupported V1/prototype machine or development project state; drwn does not infer provenance or migrate it. Portable inventory transfer excludes machine intent, Worker locks, Cards, credentials, generated output, and write records.
